# Project explanation

## Simple explanation

A Weather Forecast & Alert Application lets someone look up a place and see its current weather and upcoming forecast. It checks the weather values against clear rules and highlights conditions that may need attention, such as likely rain, high temperatures, strong wind, or poor air quality. The project combines a Python API, a public weather data provider, and a dashboard.

For example, a traveler can check rain before leaving, an event planner can review the week before an outdoor event, and a delivery team can identify windy or wet conditions that could affect routes. A farmer can use the forecast as one input when planning field work. It is a planning aid; users should rely on local authorities for official warnings and safety instructions.

## What problem does it solve?

Weather information is available from many sources, but users often have to switch between forecast pages, interpret several measurements, and decide which conditions matter to them. This app gathers the information for a selected location, presents it in one dashboard, and applies visible, understandable thresholds to surface possible risks.

It helps users notice conditions sooner and compare forecast days. It does not guarantee that a forecast will occur or replace professional or official advice.

## Who can use it?

- **Everyday users and travelers:** check current conditions and prepare for rain, heat, or wind before a trip or commute.
- **Businesses and logistics teams:** use forecasts as one input when planning deliveries, staffing, and outdoor operations. A production deployment would need service-level monitoring and carefully validated alerts.
- **Farmers:** review upcoming temperatures and precipitation when planning work. The current project is not an agricultural decision system and does not include soil, crop, or irrigation data.
- **Event planners:** review forecast trends and possible weather disruptions before outdoor events.

## How weather APIs provide live data

A weather API is a web service that accepts a request and returns structured data, usually as JSON. The application sends the requested city to a geocoding service to find its latitude and longitude. It then requests current conditions and forecast values for those coordinates. The provider response can include timestamps, temperature, precipitation probability, wind speed, and daily forecast summaries.

This project uses Open-Meteo's public geocoding and forecast endpoints, and requests current US AQI from its air-quality endpoint. The Python service converts provider-specific field names into a consistent response for the dashboard. When AQI is unavailable, it is represented as missing rather than estimated. Responses are cached in memory for ten minutes to reduce repeat requests.

## How the application generates alerts

An alert is generated by comparing a weather value with a configured threshold. For example, if the rain probability reaches the project's high-risk threshold, the API returns a high rain alert with a short explanation. Each alert has a level, category, title, and message, so the dashboard can display it consistently.

The current implementation includes these educational defaults:

| Condition | Moderate alert | High alert |
|---|---:|---:|
| Rain probability | 40% | 70% |
| Precipitation amount | — | 20 mm |
| Temperature | 35°C | 40°C |
| Relative humidity | 85% | 95% |
| Wind speed | 40 km/h | 60 km/h |
| US AQI | 101 | 151 |

Humidity is checked using the thresholds above. The app also raises a storm alert when Open-Meteo explicitly reports WMO weather code 95, 96, or 99. High precipitation or wind alone is not treated as proof of a storm. These thresholds are project examples, not locally calibrated or official warning levels.

## Workflow

```text
User enters a city
        ↓
Geocoding API resolves the city to coordinates
        ↓
Weather API fetches current conditions and forecasts
Air-quality API supplies US AQI when available
        ↓
Python service normalizes fields and handles optional/missing data
        ↓
Alert rules compare measurements with configured thresholds
        ↓
FastAPI returns a structured JSON response
        ↓
Streamlit displays metrics, notifications, charts, and a map
        ↓
Generate and download a CSV report snapshot
```

The dashboard can generate and download a CSV report containing current readings, forecast rows, and alerts; the API also writes a copy to `outputs/`. There is no report database or searchable history yet. To add that, introduce a storage layer (for example, SQLite) and a report model containing the location, timestamp, forecast, and alerts. Simulation mode follows the same response, alert, and report workflow without making external API calls.

## Technical explanation

The Streamlit frontend sends an HTTP request to FastAPI's `/weather` route. FastAPI validates the query parameters. The service resolves a city through Open-Meteo Geocoding unless latitude and longitude were supplied directly, then calls the Forecast and Air Quality endpoints asynchronously. It normalizes the provider response into `location`, `current`, `hourly`, and `daily` objects, runs the pure rule function in `src/weather_app/alerts.py`, and returns JSON. The dashboard renders that response using Streamlit metrics, Plotly charts, and a geographic plot.

Live provider failures are reported as API errors instead of being silently replaced with sample data. Simulation mode is deterministic, explicitly labeled, and intended for offline demonstrations. The cache is process-local and resets when the API restarts.

## Example user journey

1. A traveler enters “London” in the dashboard.
2. The API geocodes London to coordinates.
3. The service requests current weather, hourly values, a seven-day forecast, and AQI if available.
4. The service shapes these values into the project's response format.
5. The alert function checks rain, temperature, humidity, wind, and AQI against the thresholds.
6. The dashboard shows current measurements, any alerts, hourly and daily charts, and the location on a map.
7. The user can download the snapshot as a CSV report; persistent history could store it for later comparison.
